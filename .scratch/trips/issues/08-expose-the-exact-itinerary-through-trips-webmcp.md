# 08: Expose the exact itinerary through Trips WebMCP

**What to build:** Register bounded Trips WebMCP tools only while a private Trips route and its Trip Document are visible. A chosen browser agent can retrieve the exact current itinerary and revision, search bounded Library sources, create a trip after an explicit request, validate stored facts, and apply exact user-instructed changes through the same Trips module used by the human UI. Tool results update the visible artifact immediately; navigating away removes the tools cleanly.

**Blocked by:** 05: Plan with Library sources and Unscheduled entries.

**Status:** done

- [x] `list_trips` returns bounded summaries for the authenticated Library and cannot reveal another Library's Trip Documents.
- [x] `get_trip` returns the exact visible Trip Document: revision, setup context, ordered days, ordered stops, Unscheduled entries, references, decision/provenance state, holes, stored facts, and current advisory flags. It does not expose private account/session data or unrelated Library content.
- [x] `search_trip_sources` searches bounded Item and Place summaries in the current Library without returning arbitrary database rows or complete unrelated captions.
- [x] `create_trip` requires a user-authorized call and uses the same setup validation and ownership rules as the human UI.
- [x] `apply_trip_changes` accepts only documented typed operations, an expected revision, a client mutation id, and an optional originating user instruction. Actor is derived from the trusted WebMCP adapter.
- [x] Exact instructions may update the Trip Document atomically. Open-ended taste questions are rejected from direct-write operations and directed to the recommendation presentation contract instead.
- [x] `validate_trip` reports deterministic conditions present in saved Trip Document data—such as overlaps, ordering errors, duplicate identities, reservation conflicts, unfilled holes, and stale user-stored facts—without inference, route lookup, or open-web access.
- [x] Tools register through the proven target-browser WebMCP lifecycle only for the visible private trip, abort/unregister on route or document change, and re-register once without duplicates when the surface returns.
- [x] Adapter tests cover schemas, bounds, stable stale/invalid/not-found/forbidden results, Library isolation, actor derivation, idempotency, and forbidden consequential actions. A real-browser regression test discovers and invokes every tool, verifies visible updates, navigates away, and confirms cleanup/re-registration. Relevant module tests, typecheck, and build remain green.

## Comments

`app/src/trips-webmcp.ts` clones the Reading proving-slice lifecycle (AbortSignal cleanup, one active registration, no-op without a runtime, no React/MCP SDK) with six tools: `list_trips` (capped at 50 summaries), `get_trip` (visible document by default, explicit id override, `advisories: []` until ticket 09), `search_trip_sources` (reuses `searchTripSources`, q ≤ 120), `create_trip` (setup passed through to the module that owns validation), `apply_trip_changes`, and `validate_trip`. Schemas declare objects with `additionalProperties: false`; unknown input keys are ignored and never forwarded, and no input accepts `libraryId`/`actor`. Errors map by duck-typed HTTP status: 400 → `invalid`, 403 → `forbidden`, 404 → `not-found`, 409 → `stale`. Prose without typed operations returns `invalid` with a detail naming `present_trip_recommendations`; no publish/revoke/delete/undo/confirm tool exists.

Trusted-adapter boundary: new HTTP route `POST /api/trips/:id/agent/changes` (server/http/server.ts) calls `applyTripChanges(…, "agent")`, so agent-added and agent-replaced stops begin Draft exactly as ticket 07 defines — the body never names an actor or Library. `validateTripDocument` (server/trips/projections.ts) is a pure projection check: ranged-window overlaps (reusing overview conflicts), unfilled holes, duplicate stop identities, and position/order mismatches; reservation conflicts and stale stored facts are honestly absent because no such data exists yet. TripsPage attaches the host on all three private Trips routes (`#/trips`, `#/trips/new`, `#/trips/:id`), re-registers on document change via deps `[mode, tripId]`, and the host dispatches `locus:trip-updated` after an agent apply so `TripDocumentPage` swaps React state — the visible artifact updates without a reload, like a human edit.
