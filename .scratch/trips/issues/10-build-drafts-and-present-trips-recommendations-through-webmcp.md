# 10: Build drafts and present Trips recommendations through WebMCP

**What to build:** Complete the user-directed Trips WebMCP workflow. After a clear request, an agent can build one coherent Draft itinerary from the Trip Document's user-entered context and bounded Library sources. Later exact instructions use the existing exact-change tool. Open-ended taste decisions use a dedicated recommendation presentation tool that places three opinionated choices into the approved visible drawer/sheet for the user to select; the agent cannot choose on the user's behalf.

**Blocked by:** 07: Review drafts, holes, and recommendations; 08: Expose the exact itinerary through Trips WebMCP.

**Status:** done

- [x] `build_trip_draft` requires a Trip Document id, expected revision, client mutation id, originating user instruction, and bounded selected-source scope.
- [x] One base-build call creates one atomic Trip Changeset. Every generated stop begins Draft, carries actor and source provenance, and appears immediately in the visible Day Planner, Overview, and Schedule.
- [x] The build may use only the Trip Document context and bounded Item/Place summaries retrieved through approved tools. It cannot crawl the web, read unrelated Library content, or silently create Items and Places.
- [x] Any inferred preference is visibly identified as an inference, linked to its Library basis, and removable by the user; it is not rewritten as user-entered context.
- [x] `present_trip_recommendations` requires exactly three bounded options for one explicit open-ended request or hole. Each option includes opinion, fit, tradeoff, provenance/basis, proposed typed changes, and likely effect.
- [x] Recommendation presentation is temporary page state like Reading recommendations. No option mutates the Trip Document until the user selects it through the human UI.
- [x] The human may inspect, dismiss, choose, or adjust an option. Selection applies one human changeset after rechecking the current revision; stale selections fail safely and preserve the latest itinerary.
- [x] WebMCP has no tools for publishing/revoking a share, deleting a Trip Document, impersonating a human actor, or bypassing Draft review.
- [x] Module/adapter tests cover atomic base builds, Draft enforcement, bounded source scope, stale rollback, inferred-preference attribution, exactly-three schemas, option sanitization, and selection against a changed revision. Browser tests invoke both tools through the target runtime and verify visible Drafts, rich recommendation choices, dismissal, human selection, route cleanup, and no hidden inference on page open. Relevant existing tests, typecheck, and build remain green.

## Comments

`app/src/trips-webmcp.ts` gained two tools on the existing register/abort lifecycle (toolset is now eight, nine with the review tool armed). `build_trip_draft` is a thin wrapper over the exact-change engine: selectedSources (1–12 saved Item/Place ids) become one `addStop` each on **Unscheduled** (chosen placement: always valid, races with no day edit; the human moves Drafts into days), the instruction is required and forwarded sanitized, and unknown/foreign ids reject the whole changeset server-side because references are validated by the module — the tool never creates Items/Places and never crawls. `inferredPreferences` (0–8 `{text, basis}`, sanitized) ride the same atomic changeset: `applyTripChanges` accepts them for the agent adapter only, writes them into a new `trips.inferences_json` (schema v16, additive ALTER with PRAGMA guard) inside the same transaction, and includes them in the replay hash, so a stale or partially invalid build persists neither stops nor labels. Omitted inferences invent nothing. `present_trip_recommendations` requires exactly three options (opinion/fit/tradeoff/basis/effect ≤280, operations 1–50), sanitizes with the shared bounded-text helper, and hands the panel to `host.present` → the existing `locus:trip-recommendations` drawer; it makes zero network writes and a rejected count shows no drawer.

The document page renders a visibly separate **Inferred by agent** section (dashed card, "Inferred" chip, basis line) — never inside User-entered context — with a human Remove button posting to the new human-only `POST /api/trips/:id/inferences/:inferenceId/remove` (no /agent/ path, no revision bump, mirroring advisory dismissal). Selection, dismissal, focus trap, and stale-selection safety were already ticket-07 seams and stay green. Forbidden abilities (publish, revoke, delete, undo/redo, confirm) still never register.
